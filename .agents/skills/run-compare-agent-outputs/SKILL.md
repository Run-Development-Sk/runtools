# run-compare-agent-outputs

Skill for **comparing existing outputs** of several AI agents over the same task and recommending one solution. The inputs are files the user already has – this skill **runs no agent and spends no credits**.

## When to use

- "compare these analyses/proposals/outputs", "which of them is right", "make a recommendation out of it",
- the entry point is also the command `/run.compare-agent-outputs`.
- **Not for this skill:** the outputs do not exist yet and are to be generated by a fan-out over CLI subagents -> `/run.compare-subagent-outputs`.

## Hard rules

- **Read-only.** Read the inputs, do not modify them; the result is a **proposal, not the execution of changes**.
- **No fan-out.** Never launch `claude`/`auggie`/`codex`/`agy` to fill in a missing or weak output – report the gap instead and let the user decide.
- **Do not invent a position.** Every claim about what an agent proposes must be traceable to its file. If something is unclear or missing there, say so.

## 1. Collect the inputs

The argument may be a list of files, a glob, or a directory. If the argument is missing, ask which files to compare (offer the newest candidates in `tmp/`).

Read **each input in full** – comparing only the conclusions hides the differences that matter.

If a directory is given, look for a fan-out output in it: the proposals are `<agent>[_<model>].md`, and `prompt.md`, `specs.txt`, `manifest.tsv` are supporting files, not proposals. **Read `manifest.tsv`** if present – outputs marked `SHORT`, `FAIL`, or `SKIP` are truncated or missing, so do not compare them as if they were complete; report their status instead.

## 2. Pair a file with an agent (and model)

Derive the label from the file name and **show the mapping to the user** at the start of the comparison so they can correct it:

| File name pattern                                         | Source                                | Label                                      |
| --------------------------------------------------------- | ------------------------------------- | ------------------------------------------ |
| `<agent>.md`, `<agent>_<model>.md`                        | fan-out                               | agent + model                              |
| `<slug>-<suffix>.md` (`claude`, `auggie`, `codex`, `agy`) | `run-save-response` / `run-save-chat` | agent per the suffix                       |
| anything else                                             | unknown                               | file name; ask for the agent if it matters |

An explicit assignment from the user always wins over the file name.

## 3. Normalize the content

Inputs come in different shapes – get to the actual analysis before comparing:

- **fan-out output** – the whole file is the analysis, structured per the Output Contract (headings + a mandatory `## Conclusion / Recommendation` section); for `codex` it is only the final message (the reasoning is in the `.transcript` sidecar).
- **saved response** (`run-save-response`, `run-save-chat`) – blocks delimited by `**=+=+=+=+=+= PROMPT =+=+=+=+=+=**` / `**=+=+=+=+=+= RESPONSE =+=+=+=+=+=**` separator lines, content unindented; read the prompt block as the task the agents were solving. Files saved by older versions use `**Prompt:**` / `**Response:**` headers with the body indented by 4 spaces – strip that indentation, it is a wrapper, not content. `run-save-chat` may hold several turns – then the analysis is the whole thread, not just the last message.
- **plain free text** – take it as is.

**A missing conclusion is the normal case here** (only the fan-out enforces one). If a file has no explicit recommendation, infer the agent's position from the whole text and **mark it in the output as inferred, not quoted** – e.g. "(inferred)" next to the stance. Never present an inferred stance as the agent's own wording.

If the inputs do not answer the same task (different prompts, different scope), say so before the comparison – a comparison of answers to different questions is misleading.

## 4. Compare and analyze

Criteria: **correctness**, **completeness**, **risks**, compliance with `AGENTS.md` and project conventions, **simplicity/maintenance**.

Verify the substance against the repository (`Read`, `Grep`, `Glob`) wherever the outputs disagree on a **verifiable fact** – whether a file, field, or method exists, what the current code does. An agreement between agents is not proof; a factual error in a well-argued output is the most common reason to reject it.

## 5. Present the result

1. **Inputs** – the file -> agent/model mapping, plus a note on anything skipped (truncated output, unreadable file, different task).
2. **Table "agent/model × criterion"** – a brief assessment per criterion.
3. **Agreements** – what everyone converges on (the most reliable part of the result).
4. **Differences and factual errors** – where the outputs contradict each other and how the check against the repository turned out.
5. **Recommended solution** – one clear stance with justification, including which parts of the other proposals are worth grafting in. This is a **proposal, not the execution of changes**.
6. **Paths to the input files** so the user can verify the details.
